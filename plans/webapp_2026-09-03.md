# NYC Food Webapp — Spec (living document)

Started 2026-09-03. Branch: `webapp`. Current static page stays live on `main` until this replaces it.

## Thesis

Google Maps is a database of **places**. This is a database of **recommendations** — Kobi's opinions, dish-level tips, and crawls. Link out to Google for facts (hours, photos, directions, ratings); own the opinions. Never rebuild what Google already does well.

## Decisions (ratified 2026-09-03)

| Decision | Choice |
|---|---|
| Audience | Friends visiting NYC + broader public audience |
| Unit of content | Place + dishes + crawls, all from day one |
| Editing | Admin UI backed by a real database (phone-friendly capture) |
| Map | Lightweight embedded map (Leaflet + OpenStreetMap) alongside the list; Google Maps links for directions |
| Out of scope, permanently | Third-party reviews, star ratings, opening hours, full map engine — link to Google instead |

## What the app adds over Google Maps

1. **Dish-level recs** — "get X, skip Y." Maps has no concept of this. Core differentiator.
2. **Cross-cutting filters** — cuisine × borough/neighborhood × price × vibe × status. Maps lists are flat silos.
3. **"I'm hungry now" flow** — mobile-first: two taps → borough + vibe → a few picks with one-liners and a directions link.
4. **Crawls as first-class content** — ordered narratives (Jackson Heights, Flushing exist as concepts already). Maps structurally can't do this.
5. **Personal voice, bilingual** — formatted EN/HE notes, "why this place."
6. **Living log** — tried / want-to-try / closed / gone-downhill. History, not a snapshot.

## Stack

- **Backend:** Supabase free tier. Postgres + REST + magic-link auth. RLS: anonymous read on published rows; writes restricted to owner's email.
- **Frontend:** static SPA on GitHub Pages (build with Vite; framework TBD at implementation — lean, no heavy meta-framework). Leaflet + OSM tiles for the map view.
- **Admin:** same app, `/admin` route behind Supabase auth. Forms usable from a phone.
- **Analytics:** keep GoatCounter (`kobim`), carry over event-name continuity where events map 1:1.
- **Known limitation (v1):** client-side rendering → poor SEO. Acceptable for launch; pre-rendering/static snapshot is the future fix if the broader audience materializes.

## Data model (sketch)

```
places
  id, slug, name
  borough, neighborhood
  cuisine_tags text[], vibe_tags text[]
  price_tier (1–4)
  status (recommended | want_to_try | closed | demoted)
  gmaps_url, lat, lng
  note_en, note_he
  published bool
  created_at, updated_at

dishes
  id, place_id → places
  name_en, name_he
  note_en, note_he
  must_order bool
  sort_order

crawls
  id, slug
  title_en, title_he
  intro_en, intro_he
  published bool

crawl_stops
  id, crawl_id → crawls, place_id → places
  stop_order
  note_en, note_he   -- "get X here, then walk two blocks…"
```

Bilingual rule: Hebrew may lag; UI falls back to English when a `_he` field is empty. Don't block publishing on translation.

## Seeding

Initial data comes from the five existing Google Maps lists. The short links are opaque — **owner must confirm which list each URL is** (pizza/coffee were swapped once). Owner exports or dictates the places; do not guess.

# Product spec v2 (2026-09-13)

Extends v1 above. v1's ratified decisions stand — including hours out of scope (re-confirmed today after a cost discussion). New this session: the real seed data landed, the admin/curation UI is defined as the first deliverable, and the Google-enrichment policy is settled field by field.

## Decisions (ratified 2026-09-13)

| Decision | Choice |
|---|---|
| Import scope | **NYC food/drink only.** Triage sees the whole Takeout export, but only NYC food places enter the DB. Other cities / non-food lists stay in the export for a future decision. No `city` field needed. |
| Cleaning UI | **It IS the admin UI.** No throwaway tool. Importing/triaging the Takeout data is the admin UI's first job; the same screens later serve day-to-day editing and quick-add. |
| Labels model | **Structured facets + curated tags.** Facets (dedicated fields, drive filters): cuisine, borough/neighborhood, price tier, status. Tags (owner-managed controlled list, also filterable): kid-friendly, has-seating, street-food, vegetarian-friendly, vegan-friendly, … Free-form-per-place tags rejected (typo/near-duplicate mess). |
| Google enrichment | **Essentials + Pro tiers only, refreshed monthly.** Never touch the Enterprise tier (hours, phone, website — all covered by the Maps link-out). $0/month at ~4× current scale; API quota caps set at free-tier limits so overage is structurally impossible. Requires a Google Cloud account with a card. |
| Freshness rule | Any Google-sourced field shown publicly is refreshed **at least monthly, or not shown at all.** Owner-owned and static fields are exempt by construction. |
| Price level | Shown publicly ($–$$$$), from Google, monthly refresh, also a filter facet. |
| Business status | Never shown raw. Monthly check feeds an **admin closure alert** ("Google says closed") → owner confirms → status set to `closed`. |
| Tag pre-fill | **One-time at import only:** Google attributes (kid-friendly, outdoor seating, serves vegetarian, takeout) become tag *suggestions* the owner approves/rejects in triage. Never re-fetched; tags are owner-owned after that. |
| Phone / website | Not shown. Maps link covers them. |
| Opening hours | Not shown (v1 decision stands). Maps link covers them. |

## Source data (materials/Takeout, exported 2026-09-13)

Reality is bigger than v1 assumed: **43 CSV lists, ~1,080 rows**, not five lists.

- CSV shape: `Title, Note, URL, Tags, Comment`. Tags/Comment are empty in practice. Notes are mixed Hebrew/English; some are dish-level gold, many rows have none.
- The URL embeds a stable Google place identifier → usable for cross-list dedup and Places API lookups. No coordinates in the CSVs.
- `Maps (your places)/Saved Places.json`: 180 default-saved places **with lat/lng, address, and CID** — a second source to cross-link.
- Largest list is "Kobi's list of food to try" (~395 rows). Many lists are out of scope (Israel, Barcelona, London, SF, parks, galleries, shops, bars).
- Expected DB size after triage: **~150–250 NYC food places.**

## Field model — every place field has exactly one class

| Class | Refresh obligation | Fields |
|---|---|---|
| **Owner-owned** | none (can't go stale) | name-as-displayed, notes EN/HE, dish recs, status, rec source, tags, crawl membership |
| **Static** | fetched once, can't rot | Google place ID, Google Maps link |
| **Refreshed** | monthly job, else don't show | coordinates, address, neighborhood (Essentials); price level, business status (Pro) |

New owner fields vs. the v1 schema sketch:

- `rec_source` (text, admin-only in v1) — where the rec came from: a friend's name, "Instagram", "YouTube". Often already living inside imported notes; triage can split it out.
- Visited-or-not is **not a new field** — it's the existing `status` enum: `recommended` = tried & endorse, `want_to_try` = untried rec, plus `closed`, `demoted`. Public filter "been there / on the list" maps to recommended vs. want_to_try.
- `place_id` (Google), `price_level`, `business_status` (admin-only), `tags` move from `vibe_tags text[]` sketch to a proper curated-tag relation.

## Phases

**Phase 1 — Admin UI, triage mode (first deliverable).** Import all 43 CSVs + Saved Places.json into a staging table, then a keyboard-fast review flow, one place at a time or list-by-list:

1. Keep / drop (default-drop non-NYC and non-food lists wholesale, with per-row override).
2. Dedup: same place ID across lists → merge into one place, union the notes, show which lists it came from.
3. Per kept place: set status (tried vs. want-to-try), rec source, edit/translate notes, approve/reject pre-filled tag suggestions, set cuisine + neighborhood facets.
4. One-time Google enrichment on kept places (coordinates, address, price, attributes-for-tag-suggestions).

Progress must be resumable — 250+ places won't be triaged in one sitting.

**Phase 2 — Public app** (per v1: list + Leaflet map, filters by cuisine × neighborhood × price × status × tags, place pages with dish recs, bilingual EN/HE with EN fallback, Maps link-outs, crawls as ordered narratives with intro + per-stop notes).

**Ongoing — two standing flows:**

- **Quick-add:** paste a Google Maps link into admin → resolve place ID → fetch Essentials+Pro fields → draft place for owner to finish (status, notes, tags). Same flow works via a Claude session with DB access ("here's a link, add it").
- **Monthly refresh job:** re-fetch refreshed-class fields for all places; diff → closure alerts. Likely a scheduled GitHub Actions job (free), key in secrets — final call at implementation.

## Cost model

$0/month steady state. One-time import ≈ 250 Pro-tier calls (5,000 free/mo). Monthly refresh ≈ 250 Pro calls (break-even at 1,000+ places). Quota caps at free-tier limits in Cloud console = no surprise-bill risk. Supabase free tier + GitHub Pages + GoatCounter as in v1.
